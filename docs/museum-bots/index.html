Два бота, которые делают музей: Archivessa и Chartessa

Концепт: автономный конвейер проверенных находок + бот личных стеков-карточек поверх архива · концепт, собрано 2026-10-14

Короткий ответ. Да, я это соберу. И да — Chartessa-бот имеет смысл: он забирает у меня ровно ту половину работы, которую я делаю хуже всего, а именно интерфейс для человека. Archivessa производит проверенное знание, Chartessa делает из него личные инструменты, которыми можно пользоваться руками.

Статус: боты созданы 14.10.2026 — профили archivessa и chartessa (клон моей конфигурации: та же модель, те же скиллы), у каждого свой SOUL.md с миссией и правилами, свои assets/avatar.png и заголовок роли. Аватарки и вид ботов выбраны пользователем вручную, поэтому в profile.yaml стоит ui_meta.hermes-bots.custom: true — дефолтная генерация их не перезапишет.

Ниже — концепт, а не мечта: каждый шаг привязан к реальному примитиву Hermes (профили, cron-рутины, kanban, делегирование, скиллы), а в конце — MVP с точными командами.

1. Почему два бота, а не один

КритерийArchivessa (контент)Chartessa (интерфейс и инструменты)
Ритмчасовой/суточный, автономныйотзывчивый, по запросу человека
Тип работыпоиск, проверка, сведение данныхсборка материальных «вещей»: стеков, карточек, кнопок
Риск-профильсамый опасный: выдуманный фактсамый мягкий: плохой интерфейс видно сразу
Памятьисточники, дедупликация, история проверокпредпочтения человека, шаблоны, привычные стеки
Отказдолжен молчать, если нечего сказатьдолжен отвечать всегда, даже частично

Один бот с двумя характерами начнёт компромиссно делать и то и другое. Два профиля = две памяти, два набора скиллов, два расписания и возможность работать параллельно. В Hermes каждый бот — это профиль (hermes profile create archivessa), у него своя папка ~/.hermes/profiles/<bot>/, свои скиллы, своя память, свои сессии и свои рутины (cron-задания, которые видны как [bot:<name>] <routine> в hermes cron list и складывают результат прямо в чат этого бота).

Всё, что дольше одной минуты — это уже не cron, а kanban-карточка, которую диспетчер поднимет отдельным воркером и не потеряет при перезапуске: делегированные дети живут только внутри процесса родителя, kanban — нет.

2.4 Жёсткие правила Archivessa

  1. Нет цитаты — нет записи. Каждая фактическая фраза проходит проверку дословной цитатой из скачанного текста; не прошла — запись не публикуется.
  2. Провенанс не размывается. Источник, прочитанный целиком, помечается r:1 (в интерфейсе ✓), источник уровня поискового индекса — r:0 (↗).
  3. Архив не удаляет. Устаревшая находка переписывается с пометкой, а не исчезает.
  4. Ничего из головы модели. Не нашлось подтверждения — фраза не попадает в дайджест вообще (так уже выпала история про торговое давление США на BTRON).
  5. Суждение помечено суждением. gap и «что внедрить» — вывод агента, и это написано и в интерфейсе, и в футере.
  6. Уважение к источникам. Не больше одного запроса в секунду на хост, соблюдение robots.txt, никакой перепубликации чужих текстов — только ссылки и короткие цитаты.
  7. Бюджет. Не больше N новых записей за цикл и не больше M воркеров одновременно: музей должен расти, а не сжигать лимиты.

3. Бот 2 — Chartessa: личные инструменты на базе архива

3.1 Метафора HyperCard (1987), перенесённая в LLM

HyperCard (1987)Что это теперь
карточка (card)блок данных: заголовок, поля, ссылки, медиа, один вопрос
фон (background)шаблон карточки: сравнение, таймлайн, «до/после», таблица источников
кнопка и скриптограниченное действие, которое отправляет промпт с полями карточки как контекстом
стек (stack)набор карточек = готовый инструмент («мой стек по агентным протоколам»)
домашний стек (home)витрина стека и переходы между стеками
режим browse и authorпросмотр vs правка: человек правит словами, бот правит данные

Ключевой момент: скриптовый слой больше не пишут на HyperTalk. Кнопка отправляет промпт, а инструменты, которые агенту разрешены в этом действии, ограничены списком. Это тот же HyperCard, только действие описывается словами, а безопасность обеспечивается белым списком инструментов, а не песочницей языка.

3.2 Формат стека

stacks/<slug>/stack.json     карточки, фоны, связи, действия
stacks/<slug>/index.html     результат сборки, руками не правится
stacks/<slug>/assets/        картинки и прочее (с проверкой лицензии)

Поля карточки: id, title, background, fields (свободные данные), links (двусторонние, как у Xanadu), actions (промпты), sources (ссылки). Стили и разметка генерируются из шаблона templates/stack.html, как и у дайджестов: человек и бот правят данные, а не HTML.

3.3 Что он умеет практически

  1. Собрать стек по запросу: «сделай карточки по агентным протоколам 90-х и сравни с MCP» → стек с полями и источниками.
  2. Сравнивать: карточка-фон «до/после» для пары «что было — что стало».
  3. Действовать: кнопка на карточке запускает ограниченный промпт («найди современный аналог», «проверь, жив ли проект», «добавь источник»).
  4. Связывать: двусторонние ссылки между карточками и записями архива (идея Xanadu, которая так и не прижилась в вебе).
  5. Собирать инструмент, а не читать: стек — это не отчёт, а рабочая вещь, которую можно листать и которой можно пользоваться.

Разделение писателей — главная защита от конфликтов: в data/ пишет только Archivessa, в stacks/ — только Chartessa. Оба публикуют через один и тот же scripts/build.py, поэтому сайт остаётся согласованным.

5. MVP: три итерации до работающей системы

Итерация 1 — фундамент (полдня). Боты созданы (см. «Статус» выше); остаётся скриптовая часть:

hermes profile create archivessa
hermes profile create chartessa
hermes profile describe archivessa "Производит проверенные дайджесты для музея потерянных идей"
hermes profile describe chartessa "Собирает личные стеки-карточки поверх архива музея"

В репозиторий добавить archivessa/watchlist.json, scripts/scan.py (только stdlib: RSS/Atom, HN Algolia, arXiv API), scripts/queue.py (дедупликация и статусы). Проверка готовности: python scripts/scan.py кладёт кандидатов в очередь и повторный запуск не даёт дублей.

Итерация 2 — цикл публикации. Скилл lost-tech-museum скопировать в профиль Archivessa, добавить рутины:

hermes cron add "0 */6 * * *" --name "[bot:archivessa] scan"  --script scripts/scan.py --no-agent
hermes cron add "0 9 * * *"   --name "[bot:archivessa] triage" --skill lost-tech-museum,grounded-citations
hermes cron add "0 10 * * 1"  --name "[bot:archivessa] publish"

Проверка готовности: ручной прогон триажа создаёт kanban-карточки, прогон публикации обновляет сайт и уведомляет человека ровно один раз.

Итерация 3 — Chartessa. templates/stack.html, скилл stack-author, поддержка stacks/ в scripts/build.py, домашний стек-витрина. Проверка готовности: по одной фразе человека появляется стек с карточками, источниками и работающими кнопками, и он открывается как обычная страница сайта.

7. Что считаем успехом

  1. За месяц архив вырос не менее чем на 10 проверенных записей, и ни одна не отозвана как выдуманная.
  2. Каждая запись имеет минимум один прочитанный целиком источник.
  3. Человек получает уведомление только тогда, когда действительно есть что смотреть.
  4. Хотя бы один стек Chartessa используется повторно через неделю после создания.
  5. Новый дайджест от идеи до живой страницы — без ручных команд в HTML.

8. Что нужно решить вам

  1. Имена ботов. Решено: профили archivessa (Хранительница архива) и chartessa (Собирательница стеков) уже созданы, аватарки выбраны вами.
  2. Агрессивность. Сколько новых записей в неделю считаем нормой: спокойно (3–5) или настойчиво (10+)?
  3. Уведомления. Куда присылать дайджест-алерты: только в этот чат, или ещё в мессенджер (Telegram и т.д.)?

Скажете «поехали» — и я начну с итерации 1: два профиля, скрипт скана и список наблюдения.

9. Рутина конвейера: scan → очередь → триаж → публикация

Ниже — фактический порядок от 14.10.2026, проверенный запуском (не проект, а то, что реально работает). Сканер — hubd (/home/lain/.hermes/profiles/libraressa/workspace/hubd), музей читается только на чтение.

1. Список наблюдения собирается из архива, а не пишется руками.

cd /home/lain/.hermes/profiles/libraressa/workspace/hubd
python3 -m hubd watchlist --museum ../lost-tech-museum --out watchlist.json
# источников: 47 (уникальных адресов: 47) → watchlist.json

В список попадают статусы и ленты изменений RFC, на которые ссылается архив, первоисточники записей и сам сайт музея. Хосты вне «архивного» списка (вики, новости, копии докладов с учебных кафедр) пропускаются — поэтому мёртвые ссылки из записей сюда не попадают (см. п. 7).

2. Обход и очередь кандидатов.

python3 -m hubd serve --store data/hub.json --port 8765 --retry-interval 5   # отдельным терминалом
python3 -m hubd scan --watchlist watchlist.json --state data/scan.json \
    --queue data/candidates.jsonl --hub http://127.0.0.1:8765 --once        # или --every 300
python3 -m hubd candidates --file data/candidates.jsonl --status new --show-sample

Кандидат — это (тема, адрес, отпечаток содержимого). Первый обход источника — знакомство, а не новость: событие появляется только когда отпечаток реально изменился. Возврат источника к уже разобранной версии публикуется подписчикам, но дубля в очереди не создаёт.

3. Триаж — работа хранителя, не скрипта. Для каждого кандидата: прочитать первоисточник, выписать дословные цитаты с URL и решить — это правка записи, дубликат или отказ.

python3 -m hubd candidates --file data/candidates.jsonl --accept <id кандидата>
python3 -m hubd candidates --file data/candidates.jsonl --reject <id кандидата>

Оговорка, проверенная запуском: опции --reason у CLI нет (hubd: error: unrecognized arguments, код 2), и в строке очереди нет поля причины — статус ставится без неё. Поэтому причина отказа живёт в журнале docs/triage-log.md, а строка очереди получает её отдельным шагом (поле note). Отказ не удаляет кандидата: статус rejected + причина — принцип «архив не удаляет» действует и здесь.

4. Правка архива. data/*.json — единственный писатель Archivessa; у каждого источника, на который опирается утверждение, поле q с дословной цитатой. Если источник заменён — в тексте записи остаётся пометка, что источник менялся.

5. Проверки перед публикацией (все три обязаны быть зелёными).

python3 scripts/quotes.py --fetch      # каждая цитата против скачанного первоисточника; код 1 — публиковать нельзя
python3 scripts/build.py               # сборка сайта + проверка страниц
python3 scripts/lint_stacks.py         # целостность стеков

6. Публикация.

git add -A && git commit -m "digest: …" && git push     # Pages обновляется сам

7. Сторож и замкнутый контур. Среди 47 источников есть сам сайт музея. После публикации его ETag меняется, сканер кладёт кандидата museum/site, и триаж отклоняет его с причиной «наша же публикация, находки нет». Это не шум, а подтверждение, что робот действительно видит наш сайт.

Чего рутина не делает (и что заменяет пробел). Сканер ловит только изменения источников. Утверждение без цитаты и мёртвая ссылка изменениями не являются — их ловит аудит записей: обход адресов из data/*.json (включая те, что не попали в список наблюдения) с --fail-on-error, чтобы cron получал код 1.

python3 -m hubd check --watchlist watchlist-audit.json --state data/scan-audit.json --fail-on-error

Cron не заведён. Расписание из §2.3 остаётся проектом: постоянные рутины не создаются без отдельного подтверждения владельца.
