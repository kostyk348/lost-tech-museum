# Журнал триажа: очередь hubd → записи архива

Прогон: 14.10.2026. Очередь: `hubd/data/candidates.jsonl`. Решение принимает хранитель архива
(Archivessa); статус ставит CLI `hubd candidates --accept/--reject`, причина живёт здесь — опции
`--reason` у CLI нет (см. «Интерфейс» в конце).

## Как наполнилась очередь

1. **Базовый обход 47 источников** на пустой очереди:

   ```
   $ python3 -m hubd scan --watchlist watchlist.json --state data/scan.json \
       --queue data/candidates.jsonl --hub http://127.0.0.1:8765 --once
   изменений нет (47 источников)
   источник недоступен: https://www.oasis-open.org/…/uddi-v3.0.2-20041019.htm —
       источник недоступен (IncompleteRead: IncompleteRead(2051509 bytes read))
   ```

   Ноль кандидатов — и это правильно: первый обход источника это знакомство, а не новость.
   Обрыв на странице OASIS 2.1 МБ записан и обход не уронил.

2. **Прогон триажа на живых данных.** Чтобы разобрать конвейер, не дожидаясь изменений в сети,
   состояние обхода скопировано, у 5 источников отпечаток заменён на заведомо чужой и сняты
   валидаторы (иначе сервер отвечает `304` и события не будет):

   ```
   $ python3 -m hubd scan --watchlist watchlist-triage.json --state scan-seeded.json \
       --queue data/candidates.jsonl --hub http://127.0.0.1:8765 --once
   изменился https://datatracker.ietf.org/feed/document-changes/rfc1752/ → публикация 200: …
   кандидатов новых: 5, уже были в очереди: 0 (всего 5)
   ```

   Это имитация **события**, а не выдумка **содержания**: тела и отпечатки кандидатов скачаны
   сканером из сети (sha256 совпадает с отпечатком источника в состоянии обхода).

## Решения

| кандидат | источник и что в нём | решение | причина |
|---|---|---|---|
| `3f1f1bad70b4f423` `rfc/rfc1752/changes` | лента изменений RFC 1752: 14.08.2026 — `added errata tag`, затем `added verified-errata tag` | принят | живое изменение первоисточника: у RFC 1752 появилась подтверждённая errata **EID 9133**. Она типографская (в разделе 6.1 пропущен пробел между «of» и «IPng»), утверждения записи не меняет, но меняет состояние источника — и запись `sipp` теперь обязана это показывать |
| `57b6646899232d1f` `rfc/rfc1347/changes` | лента изменений RFC 1347: 24.05.2016 `New status of Historic approved by the IESG`, 01.12.2017 `changed standardization level to Historic` | принят | в записи `tuba` утверждение «Официально понижен до Historic» стояло **без цитаты** (источник — страница datatracker без поля `q`). Дыру в провенансе закрываем цитатой из ленты и датами |
| `6b1ab3166fe8c97e` `rfc/rfc868/changes` | лента изменений RFC 868: 29.07.2020 verified errata, 12.12.2023 `Imported membership of rfc868 in std26` | принят | утверждение «формально это Internet Standard» не имело адресного подтверждения. Добавлены стандарт **STD 26** (страница RFC Editor) и лента, обе с цитатами |
| `54dbdd9eda6f6e31` `rfc/rfc1112/changes` | лента изменений RFC 1112: 20.05.2026 служебные правки метаданных дататрейкера (ключевые слова `IGMP`, `multicast`, переименование авторов) | отклонён | изменение источника есть, но это правка каталога, а не факт: ни одного утверждения записи `ipmulticast` оно не касается. Кандидат остаётся в очереди со статусом `rejected` — архив не удаляет |
| `efd11be6d53c64bc` `rfc-graveyard/uddi` | спецификация UDDI 3.0.2 на oasis-open.org (2.1 МБ): на базовом обходе чтение оборвалось, теперь прочитана целиком | отклонён | это не изменение содержимого, а восстановление обхода после сетевого обрыва; текст спеки не менялся, новой находки нет. Побочный вывод: страница такого размера — дорогой источник для обхода |
| `63835532638c04a8` `museum/digest/rfc-graveyard` | страница дайджеста музея после нашей публикации (60446 байт, содержит `EID 9133`) | отклонён | изменение вызвано **нашей же** публикацией, внешнего факта в нём нет. Сигнал полезен как сторож: он подтверждает, что публикация доехала до живой страницы, а сканер видит наш собственный сайт |
| `b5ee366fd9c617d8` `museum/site` | главная музея после публикации | отклонён | по той же причине: изменение нашего сайта — не находка; записи не требуется |

**Сторож контура.** Последние два кандидата появились уже после `git push`, на настоящем состоянии
обхода (`hubd/data/scan.json`), а не на подменённом:

```
$ python3 -m hubd scan --watchlist watchlist-museum.json --state data/scan.json \
    --queue data/candidates.jsonl --hub http://127.0.0.1:8765 --once
изменился https://kostyk348.github.io/lost-tech-museum/digests/rfc-graveyard/ → публикация 200: … 60446 байт
изменился https://kostyk348.github.io/lost-tech-museum/ → публикация 200: … 9077 байт
кандидатов новых: 2, уже были в очереди: 0 (всего 7)
```

**Итог прогона:** кандидатов 7 — принято 3, отклонено 4, новых в очереди нет. Все семь строк очереди
остались на месте со статусом и причиной (`note`): отказ не удаляет кандидата.

**Что изменилось в архиве по принятым кандидатам**

* `data/rfc-graveyard.json`, запись `sipp`: добавлены два источника с цитатами —
  `rfc/inline-errata/rfc1752.html` (`EID 9133 (Verified) is as follows:`) и лента
  `feed/document-changes/rfc1752/` (`Update from RFC Editor: added verified-errata tag`);
  в тексте записи — пометка о errata и о том, что утверждения записи она не меняет.
* `data/rfc-graveyard.json`, запись `tuba`: добавлен источник-лента с цитатой
  `New status of Historic approved by the IESG …`; в тексте — даты решения IESG и синхронизации.
* `data/rfc-graveyard.json`, запись `time868`: добавлены `rfc-editor.org/info/std26/`
  (`STD 26 : Time Protocol`) и лента RFC 868 (`Imported membership of rfc868 in std26 …`);
  в тексте — членство в STD 26.
* **Класс решений, а не отдельный кандидат:** та же дыра (утверждение о понижении до Historic без
  цитаты) была у записи `catnip` с источником `datatracker/doc/rfc1707/`; кандидата в очереди не было,
  цитата из ленты `feed/document-changes/rfc1707/` добавлена тем же приёмом.

## Аудит записей (не кандидат сканера)

В записи `wpos` (IBM Workplace OS) висел мёртвый первоисточник
`https://srl.cs.jhu.edu/courses/600.439/ExperienceMicrokernelBasedOS.pdf`. Адрес не попал в список
наблюдения (хост не архивный), поэтому сканер его не видел — его ловит обход аудита:

```
$ python3 -m hubd check --watchlist watchlist-audit.json --state scan-audit.json
0    без изменений https://srl.cs.jhu.edu/courses/600.439/ExperienceMicrokernelBasedOS.pdf
200  без изменений https://en.wikipedia.org/wiki/IBM_Workplace_OS
202  без изменений https://doi.org/10.1109/HOTOS.1997.595173

недоступных источников: 2
  …ExperienceMicrokernelBasedOS.pdf — источник недоступен (URLError: … Name or service not known)
  https://doi.org/10.1109/HOTOS.1997.595173 — HTTP 202
```

Решение: **принято** как правка записи (аудит). Что сделано:

* мёртвая ссылка заменена на DOI `10.1109/HOTOS.1997.595173` (Rawson, HotOS 1997) — помечен `r:0`:
  IEEE отвечает `202`, для обхода это «недоступный источник», то есть прочитанным его считать нельзя,
  это идентификатор публикации;
* добавлен открытый текст того же доклада (`docslib.org/doc/3328738/…`) — `r:1` с дословной цитатой
  `it was terminated in March, 1996`. Текст — OCR скана, колонки местами перемешаны, поэтому цитата
  короткая и однозначная; о качестве скана сказано в названии источника;
* в тексте записи (`now`) — пометка «источник записи менялся» с датой: правило «архив не удаляет»
  требует пометки, а не тихой замены.

## Открытые пункты

1. ~~Причина отказа не хранится ни в строке очереди, ни в CLI~~ — **исправлено 14.10.2026**:
   `python3 -m hubd candidates --reject <ключ> --reason "…"` теперь существует (hubd `adfc8d9`,
   проверено запуском: код 0, причина ложится в поле `note` строки очереди, у решения появляется
   отметка времени `decided`). Прежнее поведение — `hubd: error: unrecognized arguments: --reason`
   (код 2) — оставлено в этом журнале как история, а не стёрто: причина отказа в тот прогон жила только
   здесь, и записи о нём менять нельзя. Триаж из первой половины этого журнала выполнялся ещё без опции.
   Мелочь к следующему разу: в очереди ключ кандидата лежит в поле `key`, а справка CLI называет его
   «id кандидата» — при ручном вызове легко подставить `id` и получить «не найден».
2. Список наблюдения строится только по «архивным» хостам, поэтому вики, новости и копии докладов
   в него не попадают. Мёртвые ссылки из записей надо ловить аудитом, иначе они живут годами.
3. Тяжёлая страница OASIS (2.1 МБ) остаётся в списке: обход её иногда не дочитывает. Решение —
   либо оставить (обрыв печатается, обход не падает), либо исключить адрес и следить за датой версии спеки.
